SuCH CHAoS OS - Codex Rules
This project simulates a modular retro operating system.

Codex must follow these rules strictly:

Naming Rules
User-facing desktop entries should use Applications, Arcade, and Shell.
Internal code names should also use applications, arcade, and shell unless an external API requires legacy wording.

Do Not
Do not rewrite entire files unless explicitly requested.
Do not remove desktop, system, or shell easter eggs unless explicitly requested.
Do not remove ASCII headers.
Do not remove HotlineDevice.
Do not modify BootScreen unless asked.
Do not break ModeRouter.
Do not inject JSX into template strings.
Do not use dangerouslySetInnerHTML.
Do not return objects instead of JSX.
Do not change unrelated logic when fixing a bug.

Shell Terminal Rules
Shell lives inside Desktop windows, not ModeRouter.
Must open one primary Shell Terminal window from the desktop.
Must open project/detail views as additional desktop windows.
Must preserve command-driven terminal flow.
Must preserve white-on-black CMD styling.
Must not infinitely scroll.
Must not use third-party terminal libraries.
Terminal typing animations must not restart from ordinary input re-renders while project or networking lists are visible.

Arcade Mode Rules
Arcade mode must not include hidden input-sequence easter eggs.
Control deck buttons must map to visible actions.
Mobile Arcade controls must retain compact but reliable tap targets.

Applications Mode Rules
Applications explorer lives inside Desktop windows, not ModeRouter.
Must preserve a left folder tree and right folder contents pane.
Must preserve a Desktop-root explorer flow: category folders first, then project folders inside each category.
Must preserve visible explorer partitions such as menu/address/status chrome and split panes.
Applications explorer chrome should stay simple and readable, not dense or overdecorated.
Applications explorer may use classic icon-view contents when that reads cleaner than dense detail rows.
Applications project data must stay separate from explorer UI components.
Applications categories must be manageable from the Control Desk: users can add a category, edit its label and summary, and delete it with confirmation when it contains projects.
The Applications editor must remain usable when no categories exist so a replacement category can be added.
Project folders must open detail windows on double-click for desktop and single tap for touch/small-screen devices.
Must not invent application icons; use blank placeholders until user-supplied retro icons are provided.
User-supplied application icons should live under public/icons/applications and be referenced from applicationsData.
Applications folder trees should use classic explorer connector lines and boxed +/- expanders, not generic list indents or modern nav styling.
Applications folder trees should stay text-first and not render folder icons in the left tree unless the user explicitly asks for them back.
Applications icon-view items in the right explorer pane should use larger frameless icons, not boxed placeholders.
Applications explorer folder tiles should use one shared folder icon for all folders, not category-specific icons.
Applications project detail windows may still use per-project icons from applicationsData.
Applications project windows should read like calm properties/preview dialogs, not secondary dashboards.
Applications UI should avoid modern chips, decorative gradients, patterned workspaces, or glassy surfaces.
Applications project windows may use classic property-sheet tabs and fieldset groups when they improve the retro feel.
Applications buttons and tabs should use square beveled Win98-style control shapes, not rounded browser-default controls.
Applications visuals should keep Win98 explorer structure but match the CHAoS OS theme, not clone Windows 98 literally.

Desktop Mode Rules
Must preserve draggable windows.
Desktop window dragging must stay smooth, pointer-based, and preserve the last dragged position across minimize/restore.
Desktop interaction animations must use Win98-style stepped frame cuts or bevel press feedback, not modern fades, blur, or smooth easing.
System monitor panels must stay below desktop windows and must not behave like top-level overlays.
Must preserve taskbar logic.
Must preserve system tray.
Taskbar controls and tray reactions must remain keyboard and touch operable.
Interactive desktop and phone controls must use native button or link semantics; invisible easter-egg probes must stay out of keyboard tab order.
Pointer desktops keep select-then-double-click icon behavior, while touch layouts open icons and folders with one tap.
Must preserve easter eggs.
Must preserve Konami code.
Must preserve CV download event.
Must preserve idle chatter.
Responsive changes may reduce secondary desktop chrome on small screens, but must preserve window access and taskbar restore behavior.
Small-screen taskbars must stay compact, single-row, aligned, and horizontally scroll task tabs instead of growing taller.
Small-screen taskbars must keep the desktop system tray controls and clock available; reduce their size instead of hiding them. The desktop mode label stays desktop-only.
Small-screen taskbar tabs must not add extra close buttons unless explicitly requested.
Desktop clock and system monitor updates must not force the full desktop/window tree to re-render.

Phone Rules
Only one HotlineDevice instance allowed.
Must receive setHotlineMsg from AppShell.
Must respond to system events.
Must stay above regular UI overlays so the phone and message bubble remain the only topmost desktop feedback layer.
Must remain visible and usable on phones; layout changes must reserve safe space for the phone and message bubble.
On small screens the phone may be compacted/docked, but it must not be hidden or removed.
Desktop idle chatter must not overwrite locked action messages.
Idle hotline messages must pass through AppShell's lower-priority channel so phone, terminal, window, and dashboard interactions stay visible for their full lock duration.
Shell Terminal phone reactions must route through Desktop's locked speak helper.
Must never duplicate.

Admin Dashboard Rules
Admin dashboard must open as a full-screen dev overlay, not a draggable desktop window.
Admin dashboard must not be registered as a visible ModeRouter mode or desktop icon.
Admin access must stay hidden behind the Shell Terminal passphrase flow, not a visible desktop icon.
Admin credentials, Supabase secret/service-role keys, and database passwords must never be hardcoded in frontend source or production bundles.
The terminal unlock phrase is only a hidden door and may be frontend-visible; it must never be treated as the real security boundary.
Admin unlock may open the full-screen dashboard on hosted builds, but editing must require Supabase Auth and Row Level Security.
The configured Supabase admin user ID must be present and must match the active Auth session; never fall back to allowing any signed-in user.
Do not prefill, display, or bundle the administrator email in the dashboard. Admin sessions must remain memory-only and must be signed out when the dashboard closes.
Admin content should load from Supabase when configured, with src/data/websiteContent.json preserved as the fallback seed.
Control Desk must provide a manual Download Backup action that exports the complete current draft as a JSON file in the browser. It must include unsaved edits, refuse to export when raw JSON is invalid, and must not create background sync tasks or automatically overwrite local fallback content.
The explicit `restore-website-backup.cmd` tool may restore a validated downloaded backup to the local fallback, but it must require an interactive Supabase Auth sign-in before publishing live content, verify the configured admin UID, use RLS-protected APIs, and never store passwords or access tokens.
An empty Supabase content row is valid. Never auto-publish fallback or seed content; publish only after a direct user edit and Save All action.
The first direct Save All action may create website_content.main through an authenticated upsert; it must remain admin-only through RLS.
Admin save tooling must write to Supabase on hosted builds and may use the local Vite file API only as a dev fallback.
Do not put Supabase secret/service-role keys, database passwords, or private credentials in frontend source.
Supabase anon/publishable keys may be used in frontend code only with RLS policies enabled.
HotlineDevice must be hidden while the full-screen admin dashboard is open, and only in that dashboard state.
Admin dashboard should prefer structured CRUD-style editors for website sections such as applications and shell projects, with raw JSON reserved as an advanced fallback.
Admin dashboard should start with a guided home/quick-actions screen rather than raw JSON.
Editable icons and images must be content-driven public paths with built-in fallbacks preserved.
The About profile image field must accept standard image formats, including animated GIFs.
Custom website assets should live under public paths or the Supabase website-assets bucket, not src imports that require code edits. Dashboard uploads must use the authenticated Supabase session, store only public asset URLs in website content, and stay within the Storage bucket's admin-only write policy.
All dashboard uploads use the same website-assets bucket, so its admin-only insert policy must cover CVs, images, icons, screenshots, and future content assets.
The CHAoS OS taskbar label and the blank taskbar area above it are separate easter-egg targets and must not trigger each other.

Architecture Protection
AppShell controls:
BootScreen
Desktop
ModeRouter
HotlineDevice

Desktop controls:
Draggable desktop windows
About and Socials windows
Shell Terminal window
Shell project/detail windows
Applications Explorer window
Applications project/detail windows
Full-screen admin overlay unlocked from Shell Terminal
Window spawning, focus, minimize, and restore

ModeRouter controls:
Fullscreen mode switching only

Never break these relationships.
